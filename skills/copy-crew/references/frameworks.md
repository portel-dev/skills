# Copywriting Frameworks

Use these structures to organize content. Pick one framework per piece. The persona determines voice; the framework determines structure.

## PAS

**Problem → Agitation → Solution**

Best for: Reddit posts, short-form content, landing pages.

```
PROBLEM:  State the pain the reader already feels.
AGITATE:  Twist the knife. Show the consequences of not solving it.
SOLUTION: Present the answer. Show code or a demo immediately.
```

Example skeleton:
```
Every time I wanted to [common task], I spent [time] on [pain].
And it's worse than you think — [consequence].
So I built [tool]. Here's what it looks like: [code/demo].
```

## Before/After/Bridge

Best for: Blog posts, product pages, longer Reddit posts.

```
BEFORE: Paint the world without your solution (specific, relatable).
AFTER:  Paint the world with it (concrete, measurable improvement).
BRIDGE: Explain how to get from before to after.
```

Example skeleton:
```
BEFORE: You write 200 lines of boilerplate for every MCP server.
AFTER:  You write 12 lines. Same result.
BRIDGE: Photon reads your TypeScript types and generates everything else.
```

## AIDA

**Attention → Interest → Desire → Action**

Best for: Product launches, Product Hunt, email announcements.

```
ATTENTION: Hook with a surprising fact or bold claim.
INTEREST:  Explain what makes this different (not features — insight).
DESIRE:    Show the result (demo, screenshot, code output).
ACTION:    One clear next step.
```

## One Reader

Write to ONE specific person with ONE specific problem. Not "developers" — one developer at 2am trying to give Claude access to their database.

```
1. Name your reader (don't publish the name, just know who they are)
2. Name their exact problem (not category — specific scenario)
3. Write as if replying to their forum post asking for help
4. Mention your tool only after genuinely helping
```

Best for: Reddit replies, community engagement, helpful content.

## Show HN Formula

Specific to Hacker News. HN rewards substance, honesty, and technical depth.

```
TITLE:   "Show HN: [Name] – [One-sentence what it does]"
         Keep under 80 chars. Be specific. No superlatives.

BODY:
1. What problem you had (personal, specific)
2. What you built (with code example or demo)
3. What's interesting technically (the non-obvious part)
4. Honest limitations (builds trust)
5. Links (GitHub, demo, video)

DO NOT: Use marketing language, exclamation marks, or "we're excited to announce"
```

## Building in Public

Best for: Twitter/X threads, indie hacker communities, ongoing engagement.

```
1. Share a specific metric or milestone
2. Explain what you did to get there (2-3 sentences)
3. Share one thing that surprised you
4. Ask the community a genuine question
```

Keep each update short. Consistency > length.

## Problem Tutorial

Best for: Dev.to, Hashnode, technical blogs. The highest-ROI content type for dev tools.

```
1. Title is the problem, not your product: "How to Stop Writing MCP Boilerplate"
2. Acknowledge the pain (show you understand the reader's world)
3. Walk through the solution step by step
4. Your tool is the vehicle, not the hero
5. Include working code the reader can copy-paste
6. Close with what else is possible
```

The reader should feel helped even if they don't use your tool.
